SQL 01 Sintaxe Básica (SQL / Databricks)

Aprenda o conceito: trilha Ordem lógica do SQL — modelo mental, exemplo para prever e erros comuns.

O que é

A estrutura de uma consulta SELECT e a ordem lógica em que suas cláusulas são avaliadas. Entender essa ordem explica por que um alias do SELECT não pode ser usado no WHERE, por que agregados são filtrados no HAVING e onde entra o QUALIFY.

Ordem lógica de avaliação

A ordem em que escrevemos não é a ordem em que a consulta é avaliada. A ordem lógica é:

FROM/JOIN → WHERE → GROUP BY → HAVING → janelas (OVER) → QUALIFY → SELECT (projeção) → DISTINCT → ORDER BY → LIMIT

O otimizador pode reordenar a execução física (por exemplo, empurrar filtros para a leitura), mas o resultado sempre respeita essa ordem lógica.

SQL
SELECT
    categoria_id,
    SUM(valor) AS receita              -- projeção: aliases nascem aqui
FROM vendas                            -- 1. origem
WHERE status_venda = 'FECHADA'         -- 2. filtra linhas antes de agregar
GROUP BY categoria_id                  -- 3. agrupa
HAVING SUM(valor) > 1000               -- 4. filtra grupos (resultado de agregados)
ORDER BY receita DESC                  -- ORDER BY já enxerga aliases do SELECT
LIMIT 10;
  • Filtre no WHERE o que não depende de agregação: reduz o volume antes do GROUP BY.
  • Use HAVING apenas para condições sobre agregados.
  • QUALIFY filtra o resultado de funções de janela (ver Window functions). É suportado no Databricks, mas não no Spark open source; fora do Databricks, use uma subconsulta com filtro sobre a coluna da janela.

Filtros: IN, BETWEEN e LIKE

SQL
SELECT *
FROM clientes
WHERE sigla_estado IN ('SP', 'RJ', 'MG')                  -- lista de valores
  AND data_nascimento BETWEEN DATE '2000-01-01'
                          AND DATE '2000-01-05'           -- inclui as duas bordas
  AND nome_cliente ILIKE 'thiago%'                        -- ILIKE: sem diferenciar maiúsculas
  AND status_conta NOT IN ('CANCELADO', 'BLOQUEADO');
  • LIKE diferencia maiúsculas de minúsculas; ILIKE não (Databricks SQL / Spark 3.3+).
  • BETWEEN em coluna TIMESTAMP com limite DATE corta o último dia em 00:00:00. Para intervalos de tempo prefira ts >= início AND ts < fim_exclusivo.
  • NOT IN com subconsulta que retorna NULL não devolve nenhuma linha. Use NOT EXISTS ou LEFT ANTI JOIN (ver Joins).
SQL
-- Retorna zero linhas se algum id_cliente em bloqueados for NULL
SELECT * FROM clientes WHERE id_cliente NOT IN (SELECT id_cliente FROM bloqueados);

-- Seguro com NULL
SELECT * FROM clientes c
WHERE NOT EXISTS (SELECT 1 FROM bloqueados b WHERE b.id_cliente = c.id_cliente);

DISTINCT com propósito

DISTINCT força agrupamento por todas as colunas projetadas e, em geral, um shuffle. Usá-lo para "corrigir" duplicidade esconde a causa (normalmente um join que multiplicou linhas).

SQL
-- Evite: deduplica tudo sem explicar de onde veio a duplicidade
SELECT DISTINCT * FROM fato_vendas;

-- Prefira: distinct sobre a chave que você realmente precisa
SELECT DISTINCT id_cliente
FROM clientes_ativos
WHERE id_cliente IS NOT NULL;

Se a duplicidade é inesperada, investigue a cardinalidade antes de deduplicar.

Operadores de conjunto

Combinam resultados de consultas com o mesmo número de colunas e tipos compatíveis. A correspondência é por posição, não por nome.

SQL
-- UNION ALL: empilha mantendo duplicatas (sem custo de deduplicação)
SELECT id_user FROM base_antiga
UNION ALL
SELECT id_user FROM base_nova;

-- UNION: empilha e remove duplicatas (equivale a UNION DISTINCT)
SELECT id_user FROM base_antiga
UNION
SELECT id_user FROM base_nova;

-- EXCEPT: o que está em A e não está em B (distinct; MINUS é sinônimo)
SELECT id_transacao FROM extrato_banco
EXCEPT
SELECT id_transacao FROM base_conciliada;

-- INTERSECT: o que existe nos dois lados
SELECT id_produto FROM catalogo_site
INTERSECT
SELECT id_produto FROM estoque_fisico;
  • EXCEPT ALL e INTERSECT ALL preservam multiplicidade — úteis para comparar tabelas linha a linha em migrações.
  • Ao contrário de =, operadores de conjunto tratam NULL como igual a NULL.

Checklist

  • [ ] Filtros de linha estão no WHERE e filtros de agregado no HAVING?
  • [ ] Intervalos de tempo usam limite superior exclusivo?
  • [ ] NOT IN com subconsulta foi substituído por NOT EXISTS quando há risco de NULL?
  • [ ] DISTINCT tem justificativa de negócio e não mascara um join errado?

SQL 02 Tipos, Conversões e Timezones (SQL / Databricks)

O que é

Comparar 100 (INT) com '100' (STRING) força conversões implícitas que podem quebrar joins, filtros e métricas sem erro aparente. Tipos explícitos estabilizam pipelines, principalmente em chaves, MERGE, datas e valores financeiros.

CAST, TRY_CAST e modo ANSI

O Databricks SQL e o Spark 4.x usam modo ANSI por padrão: CAST de um valor inválido gera erro em vez de devolver NULL. Em origens instáveis, TRY_CAST converte valores inválidos em NULL para que sejam tratados explicitamente.

SQL
SELECT
    TRY_CAST(idade_txt AS INT)         AS idade,
    TRY_CAST(flag_ativo_txt AS BOOLEAN) AS is_ativo,
    idade_txt                           AS idade_original   -- preserve para auditoria
FROM bronze.cadastro;

-- Quantos valores foram perdidos na conversão?
SELECT count_if(idade_txt IS NOT NULL AND TRY_CAST(idade_txt AS INT) IS NULL) AS invalidos
FROM bronze.cadastro;
  • Use CAST quando um valor inválido deve parar o pipeline; TRY_CAST quando ele deve ser medido e tratado.
  • Confira o modo da sessão com SET ansi_mode; (Databricks SQL) ou spark.sql.ansi.enabled (clusters).

DECIMAL para valores financeiros

FLOAT e DOUBLE são binários e aproximados: somas e arredondamentos podem divergir de uma conciliação. Use DECIMAL(p, s).

SQL
SELECT
    CAST(vlr_saldo AS DECIMAL(18, 2))   AS saldo,
    TRY_CAST(aliquota AS DECIMAL(6, 4)) AS aliquota
FROM extrato_banco;
  • p é o total de dígitos e s as casas decimais; dimensione p para o maior valor esperado mais a margem de somas.
  • Operações entre decimais podem ampliar precisão e escala; faça o CAST final na publicação.

Datas, formatos e timezone

current_date() e current_timestamp() seguem o timezone da sessão. O erro comum é misturar timestamps armazenados em UTC com sessões em outro fuso sem conversão explícita.

SQL
SET TIME ZONE 'America/Sao_Paulo';   -- fixa o fuso da sessão/job quando a regra exige

SELECT
    from_utc_timestamp(ts_evento_utc, 'America/Sao_Paulo')     AS ts_evento_br,  -- só se a origem estiver em UTC
    to_date(data_txt, 'dd-MM-yyyy')                            AS data_ref,
    to_timestamp(data_hora_txt, 'dd-MM-yyyy HH:mm:ss')         AS ts_ref,
    try_to_timestamp(data_hora_txt, 'dd-MM-yyyy HH:mm:ss')     AS ts_ref_seguro,
    date_add(DATE '2024-01-01', 30)                            AS trinta_dias_depois,
    datediff(DATE '2024-12-31', DATE '2024-01-01')             AS dias_corridos,
    date_trunc('MONTH', ts_evento_utc)                         AS inicio_do_mes
FROM logs;
  • Padrões de formato: MM é mês e mm é minuto; HH é 0–23 e hh é 1–12.
  • Com ANSI ligado, to_timestamp falha em texto inválido; try_to_timestamp devolve NULL.
  • Use literais tipados (DATE '2024-01-01', TIMESTAMP '...') para não depender de conversão implícita.

Cuidados

  • Padronize tipos antes de joins e MERGE INTO; casts dentro da condição de join escondem dados inválidos.
  • Documente a regra de timezone da pipeline: armazenamento (geralmente UTC), sessão e exibição.
  • Meça os NULL gerados por TRY_CAST em vez de descartá-los silenciosamente.

Checklist

  • [ ] O modo ANSI do ambiente é conhecido?
  • [ ] Valores monetários usam DECIMAL?
  • [ ] O fuso de origem de cada timestamp está documentado?
  • [ ] Conversões inválidas são contadas e monitoradas?

SQL 03 Sanitização de Strings e Nomenclatura (SQL)

O que é

Sanitização reduz variações de texto que dificultam joins, validações e consumo. Na passagem para Silver, aplique regras explícitas e rastreáveis; não altere valores só por estética e preserve o dado bruto na Bronze.

Limpeza básica e aliases

Projete e nomeie explicitamente as colunas publicadas. Isso torna mudanças de schema visíveis e evita transportar campos desnecessários.

SQL
SELECT
    UPPER(TRIM(cidade))    AS nm_cidade,         -- '  sao pAULO ' -> 'SAO PAULO'
    LOWER(TRIM(email))     AS ds_email,
    `Data Venda Física`    AS dt_venda,          -- nomes com espaço/acento exigem crases
    FlgAtv                 AS is_ativo           -- convenção: is_/has_ para booleanos
FROM bronze.lojas_filial;
  • Defina uma convenção (prefixos id_, dt_, vl_, is_; snake_case) e documente-a no contrato da tabela.
  • TRIM remove apenas espaços; para tabulações e quebras de linha use expressão regular.

Expressões regulares

SQL
SELECT
    REGEXP_REPLACE(descricao, '\\s+', ' ')             AS descricao_normalizada, -- colapsa espaços, tabs, quebras
    REGEXP_REPLACE(cpf_com_mascara, '[^0-9]', '')      AS cpf_digitos,          -- mantém só dígitos
    REGEXP_EXTRACT(email, '@(.+)$', 1)                 AS dominio_email,
    email RLIKE '^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$'        AS email_formato_valido
FROM bronze.usuarios;
  • Em literais SQL do Spark, a barra invertida é escapada: '\\s' vira o regex \s.
  • Regex é mais cara que funções simples (TRIM, REPLACE, TRANSLATE); use quando o padrão realmente exigir.

Remoção de acentos com TRANSLATE

TRANSLATE substitui cada caractere do segundo argumento pelo da mesma posição no terceiro. É útil para gerar chaves de comparação sem acentos ('João do Caminhão' vs 'Joao do Caminhao').

SQL
SELECT
    TRANSLATE(LOWER(nome),
              'áàâãäéèêëíìîïóòôõöúùûüç',
              'aaaaaeeeeiiiiooooouuuuc') AS nome_chave_match
FROM pdvs;
  • Use o resultado como chave de comparação, não como valor publicado.
  • A lista cobre o português comum; outros caracteres (ex.: ñ) precisam ser acrescentados. Para matching aproximado de verdade (erros de digitação), avalie funções como levenshtein e regras de negócio específicas.

Renomear colunas em tabelas Delta

Em Delta, RENAME COLUMN e DROP COLUMN exigem column mapping habilitado na tabela. Com ele, a operação altera só metadados, sem reescrever os dados.

SQL
ALTER TABLE silver.vendas SET TBLPROPERTIES ('delta.columnMapping.mode' = 'name');
ALTER TABLE silver.vendas RENAME COLUMN id_prod TO id_produto;
  • Habilitar column mapping atualiza o protocolo da tabela (leitores antigos podem deixar de ler) e pode afetar Change Data Feed e leituras em streaming dessa tabela.
  • Consumidores que referenciam o nome antigo quebram: trate como mudança de contrato.
  • Referência: Delta column mapping (Databricks).

Checklist

  • [ ] A regra de limpeza está documentada e é reversível a partir da Bronze?
  • [ ] Chaves de match sem acento são usadas só para comparação?
  • [ ] Renomeações em tabelas publicadas foram comunicadas aos consumidores?

SQL 04 Nulos e Condicionais (SQL)

Aprenda o conceito: trilha NULL e lógica de três valores — modelo mental, exemplo para prever e erros comuns.

O que é

NULL representa ausência de valor: não é string vazia ('') nem zero. Comparações com NULL resultam em NULL (desconhecido), o que afeta filtros, joins e agregações de forma silenciosa.

COALESCE e CASE WHEN

COALESCE(a, b, ...) devolve o primeiro argumento não nulo. CASE WHEN cobre regras com várias condições — sempre com ELSE explícito.

SQL
SELECT
    id_produto,
    COALESCE(nome_produto, 'SEM NOME')  AS nome_produto,
    COALESCE(id_categoria, -1)          AS id_categoria,   -- membro "desconhecido" na dimensão
    CASE
        WHEN status_atual = 'A'                   THEN 'ALTO_RISCO'
        WHEN status_atual = 'M' AND is_ativo      THEN 'MEDIO_RISCO'
        ELSE 'BAIXO_RISCO'
    END AS flag_risco
FROM silver.produtos;
  • Substituir chave nula por -1 só funciona se a dimensão tiver a linha -1 = Desconhecido; combine isso com o modelo.
  • CASE avalia as condições em ordem e para na primeira verdadeira.

NULL em agregações e comparações

SQL
SELECT
    COUNT(*)                 AS linhas,            -- conta todas as linhas
    COUNT(telefone)          AS com_telefone,      -- ignora NULL
    AVG(nota)                AS media_sem_nulos,   -- NULL fica fora do numerador e do denominador
    AVG(COALESCE(nota, 0))   AS media_nulo_zero    -- regra diferente: explicite qual é a correta
FROM envios;
  • COUNT(1) e COUNT(*) são equivalentes.
  • WHERE coluna = NULL nunca é verdadeiro: use IS NULL / IS NOT NULL.
  • Para igualdade que trate NULL como igual: a <=> b ou a IS NOT DISTINCT FROM b.
  • Em joins, chaves NULL não se correspondem (ver Joins).

Divisão por zero, NULLIF e funções try_

Com ANSI ligado (padrão no Databricks SQL e no Spark 4.x), dividir por zero gera erro DIVIDE_BY_ZERO. Escolha explicitamente o comportamento.

SQL
SELECT
    valor_bruto / NULLIF(comissao, 0)  AS fator,          -- denominador 0 vira NULL
    try_divide(valor_bruto, comissao)  AS fator_try,      -- mesmo efeito, função dedicada
    CASE WHEN comissao IS NULL THEN 1 ELSE 0 END AS is_comissao_ausente   -- flag de qualidade portável
FROM fatos;
  • iff(cond, a, b) existe no Databricks SQL, mas não no Spark open source; if(cond, a, b) existe nos dois, mas não é ANSI. CASE WHEN é portável.
  • Flags de qualidade (is_*) permitem medir o problema em vez de escondê-lo.

Checklist

  • [ ] Comparações com nulos usam IS NULL, <=> ou IS NOT DISTINCT FROM?
  • [ ] A regra de agregação com nulos (ignorar ou tratar como zero) está explícita?
  • [ ] Divisões têm política para denominador zero?
  • [ ] Chaves substitutas (-1) existem na dimensão?

SQL 05 CTEs e Views Temporárias (Databricks / Spark SQL)

O que é

Uma Common Table Expression (WITH nome AS (...)) nomeia um passo intermediário da consulta. Substitui subconsultas aninhadas por blocos sequenciais e legíveis. É uma construção lógica: não grava dados.

CTEs para organizar a lógica

SQL
WITH clientes_ativos AS (
    SELECT id_cliente, nome, estado
    FROM silver.clientes
    WHERE status = 'ATIVO'
),
faturamento AS (
    SELECT id_cliente, SUM(receita) AS valor_comprado
    FROM silver.vendas
    WHERE ano = 2025
    GROUP BY id_cliente
)
SELECT c.nome, c.estado, f.valor_comprado
FROM clientes_ativos AS c
JOIN faturamento AS f USING (id_cliente);
  • Um bloco por responsabilidade (filtrar, agregar, juntar) facilita testar cada passo isoladamente.
  • Nomeie CTEs pelo conteúdo (clientes_ativos), não pela técnica (cte1).

Views temporárias

TEMP VIEW guarda a definição de uma consulta durante a sessão (notebook ou conexão). Útil para inspecionar passos em células diferentes.

SQL
CREATE OR REPLACE TEMP VIEW v_qualidade_usuarios AS
SELECT *,
       CASE WHEN email IS NULL THEN 1 ELSE 0 END AS flag_erro_email
FROM bronze.usuarios;

SELECT * FROM v_qualidade_usuarios WHERE flag_erro_email = 1;
  • A view some quando a sessão termina e não é visível para outras sessões.
  • Global temp views (global_temp) não são suportadas em computação serverless; para compartilhar um resultado entre sessões, grave uma tabela.

Reaproveitamento e materialização

Uma CTE referenciada várias vezes pode ser recalculada a cada referência ou ter a leitura reaproveitada — depende do plano (procure ReusedExchange ou ReusedSubquery no EXPLAIN). Não presuma nenhum dos dois: observe o plano (ver Performance tuning).

SQL
EXPLAIN FORMATTED
WITH vendas_recentes AS (
    SELECT * FROM silver.vendas WHERE dt_venda >= DATE '2025-01-01'
)
SELECT 'norte' AS regiao, COUNT(*) FROM vendas_recentes WHERE regiao = 'N'
UNION ALL
SELECT 'sul', COUNT(*) FROM vendas_recentes WHERE regiao = 'S';

Quando o plano mostra recomputação cara de um passo usado várias vezes:

SQL
-- Clusters clássicos: cache em memória durante a sessão
CACHE TABLE vendas_recentes AS
SELECT * FROM silver.vendas WHERE dt_venda >= DATE '2025-01-01';
UNCACHE TABLE vendas_recentes;

-- Serverless (onde CACHE TABLE gera erro) ou resultado reutilizado por vários jobs:
CREATE OR REPLACE TABLE tmp.vendas_recentes AS
SELECT * FROM silver.vendas WHERE dt_venda >= DATE '2025-01-01';
  • CACHE TABLE e as APIs de cache não são suportados em computação serverless: limitações do serverless.
  • Tabela intermediária tem custo de escrita e de limpeza; meça antes e depois.

CTE recursiva

WITH RECURSIVE percorre hierarquias (organogramas, árvores de categorias). Disponível a partir do Databricks Runtime 17.0 / DBSQL 2025.20 (Preview).

SQL
WITH RECURSIVE hierarquia (id, id_gestor, nivel) AS (
    SELECT id, id_gestor, 0 FROM rh.colaboradores WHERE id_gestor IS NULL
    UNION ALL
    SELECT c.id, c.id_gestor, h.nivel + 1
    FROM rh.colaboradores AS c
    JOIN hierarquia AS h ON c.id_gestor = h.id
)
SELECT * FROM hierarquia;
  • O limite padrão é de 100 níveis de recursão (RECURSION_LEVEL_LIMIT_EXCEEDED); ciclos nos dados precisam ser tratados.
  • Referência: CTE (Databricks).

Checklist

  • [ ] Cada CTE tem uma responsabilidade e um nome descritivo?
  • [ ] O plano foi verificado antes de assumir recomputação ou reaproveitamento?
  • [ ] O recurso de cache/materialização escolhido existe no tipo de computação usado?

SQL 06 Agrupamentos e Pivots (SQL / Databricks)

O que é

GROUP BY resume linhas em métricas por grupo. PIVOT e UNPIVOT giram dados entre linhas e colunas. ROLLUP, CUBE e GROUPING SETS produzem subtotais em uma única consulta.

Agregações e filtros por agregação

Toda coluna não agregada do SELECT precisa estar no GROUP BY.

SQL
SELECT
    regiao,
    COUNT(*)                                           AS qtd_pedidos,
    SUM(vlr_frete)                                     AS frete_total,
    count_if(status = 'FALHA')                         AS pedidos_falhos,
    SUM(vlr_frete) FILTER (WHERE canal = 'LOJA')       AS frete_loja,
    approx_count_distinct(id_cliente)                  AS clientes_aprox
FROM silver.despachos
GROUP BY regiao
HAVING SUM(vlr_frete) > 100000;
  • FILTER (WHERE ...) e count_if evitam CASE WHEN dentro de cada agregação.
  • approx_count_distinct usa HyperLogLog++ com erro relativo padrão de 5% (relativeSD = 0.05); passe um segundo argumento menor para mais precisão (ex.: approx_count_distinct(id_cliente, 0.01)), com mais memória. Use quando a contagem exata não for requisito.
  • GROUP BY ALL (Databricks) agrupa por todas as colunas não agregadas do SELECT; prático em exploração, mas explícito é mais seguro em produção.

PIVOT e UNPIVOT

SQL
-- Linhas → colunas: um valor de ano_fiscal vira uma coluna
SELECT *
FROM (
    SELECT regiao, ano_fiscal, vendas FROM silver.vendas_anuais
)
PIVOT (
    SUM(vendas) FOR ano_fiscal IN (2023, 2024, 2025)
);

-- Colunas → linhas (Spark 3.4+ / Databricks Runtime 12.2+)
SELECT *
FROM bronze.planilha_receita
UNPIVOT (
    receita FOR mes IN (receita_jan AS jan, receita_fev AS fev, receita_mar AS mar)
);
  • A lista do PIVOT é fixa: valores novos não viram colunas automaticamente. Revise-a quando o domínio mudar.
  • UNPIVOT descarta linhas cujo valor é NULL; use UNPIVOT INCLUDE NULLS se precisar delas.

Subtotais: ROLLUP, CUBE e GROUPING SETS

SQL
-- ROLLUP: hierárquico (pais, regiao, estado) → (pais, regiao) → (pais) → total
SELECT pais, regiao, estado, SUM(volume) AS volume,
       grouping_id(pais, regiao, estado) AS nivel
FROM silver.transporte
GROUP BY ROLLUP (pais, regiao, estado);

-- CUBE: todas as combinações das colunas
SELECT ano, tipo_produto, SUM(vendas) AS vendas
FROM silver.faturamento
GROUP BY CUBE (ano, tipo_produto);

-- GROUPING SETS: só as combinações que você listar
SELECT ano, regiao, SUM(vendas) AS vendas
FROM silver.faturamento
GROUP BY GROUPING SETS ((ano, regiao), (ano), ());
  • Nas linhas de subtotal a coluna agregada aparece como NULL. Use grouping(col) ou grouping_id(...) para distinguir subtotal de um NULL real.
  • GROUP BY a, b WITH ROLLUP é sintaxe equivalente aceita pelo Spark.

Checklist

  • [ ] O grão do resultado está claro (uma linha por quê)?
  • [ ] O erro de approx_count_distinct é aceitável para o uso?
  • [ ] A lista do PIVOT cobre os valores atuais do domínio?
  • [ ] Linhas de subtotal são identificadas com grouping?

SQL 07 SQL Joins (Databricks / Spark SQL)

Aprenda o conceito: trilha Grão e cardinalidade — modelo mental, exemplo para prever e erros comuns.

O que é

Joins combinam conjuntos de dados por uma condição. Em Spark, podem exigir shuffle; o custo depende do volume, da distribuição das chaves, da estratégia física e das colunas transportadas.

Quando usar

SQL
-- INNER: somente correspondências
SELECT f.id_venda, d.uf
FROM fato_vendas AS f
INNER JOIN dim_loja AS d ON f.loja_id = d.loja_id;

-- LEFT: preserva todas as linhas da esquerda
SELECT f.id_venda, d.uf
FROM fato_vendas AS f
LEFT JOIN dim_loja AS d ON f.loja_id = d.loja_id;

-- FULL OUTER: útil para reconciliação
SELECT coalesce(a.id, b.id) AS id, a.valor, b.valor
FROM origem AS a
FULL OUTER JOIN destino AS b ON a.id = b.id;

-- CROSS: produto cartesiano intencional
SELECT c.data, f.faixa
FROM calendario AS c
CROSS JOIN faixas AS f;

LEFT SEMI JOIN retorna linhas da esquerda com correspondência; LEFT ANTI JOIN, as linhas sem correspondência. Ambos evitam carregar colunas do lado direito.

SQL
SELECT a.id FROM clientes AS a LEFT SEMI JOIN acessos AS b ON a.id = b.cliente_id;
SELECT a.id FROM clientes AS a LEFT ANTI JOIN acessos AS b ON a.id = b.cliente_id;

Cardinalidade e exploding join

O número de linhas pode crescer quando uma chave encontra múltiplas linhas do outro lado. Isso pode ser correto em uma relação 1:N ou indicar violação do grão esperado. Não deduplique automaticamente: primeiro confirme a regra de negócio e escolha uma ordenação determinística.

SQL
-- Diagnóstico do lado que deveria ter uma linha por loja
SELECT loja_id, count(*) AS quantidade
FROM dim_loja
GROUP BY loja_id
HAVING count(*) > 1;

-- Use somente quando a regra exigir a versão mais recente por loja
WITH dim_loja_atual AS (
  SELECT *
  FROM dim_loja
  QUALIFY row_number() OVER (
    PARTITION BY loja_id ORDER BY atualizado_em DESC, versao DESC
  ) = 1
)
SELECT f.id_venda, d.uf
FROM fato_vendas AS f
LEFT JOIN dim_loja_atual AS d ON f.loja_id = d.loja_id;

Performance

O hint BROADCAST pode evitar shuffle da tabela grande quando o lado transmitido cabe com folga na memória dos executores. Confirme a estratégia no plano e não force broadcast apenas por contagem de linhas.

SQL
SELECT /*+ BROADCAST(d) */ f.id_venda, d.uf
FROM fato_vendas AS f
LEFT JOIN dim_loja AS d ON f.loja_id = d.loja_id;

EXPLAIN FORMATTED
SELECT f.id_venda, d.uf
FROM fato_vendas AS f
LEFT JOIN dim_loja AS d ON f.loja_id = d.loja_id;

Para skew, prefira primeiro AQE, filtragem antecipada e revisão das chaves. Salting é uma intervenção adicional e exige medir a distribuição e preservar a semântica.

Cuidados

  • Alinhe os tipos das chaves explicitamente; casts durante o join podem mascarar dados inválidos.
  • NULL = NULL não é verdadeiro. Em Spark SQL, use <=> apenas quando nulos devam corresponder.
  • Selecione apenas as colunas necessárias para reduzir leitura e transferência.
  • Compare contagens e métricas antes e depois do join segundo o grão esperado.

Checklist

  • [ ] O grão de cada lado está declarado?
  • [ ] A cardinalidade esperada é 1:1, 1:N ou N:N?
  • [ ] Chaves têm tipos compatíveis e qualidade conhecida?
  • [ ] O plano e as métricas confirmam a estratégia escolhida?

SQL 08 Window Functions em Spark SQL

Aprenda o conceito: trilha Window functions — modelo mental, exemplo para prever e erros comuns.

O que são

Funções de janela calculam valores relacionados sem reduzir o número de linhas como um GROUP BY. A especificação combina particionamento lógico, ordenação e, quando necessário, um frame.

Exemplos

SQL
-- Versão mais recente por cliente; inclua desempate determinístico
SELECT *
FROM eventos
QUALIFY row_number() OVER (
  PARTITION BY cliente_id
  ORDER BY evento_em DESC, evento_id DESC
) = 1;

-- Comparação com a linha anterior
SELECT
  cliente_id,
  evento_em,
  valor,
  lag(valor) OVER (
    PARTITION BY cliente_id ORDER BY evento_em, evento_id
  ) AS valor_anterior
FROM eventos;

-- Acumulado desde o início da partição
SELECT
  conta_id,
  data_movimento,
  sum(valor) OVER (
    PARTITION BY conta_id
    ORDER BY data_movimento
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS saldo_acumulado
FROM movimentos;

Rows versus range

ROWS BETWEEN 6 PRECEDING AND CURRENT ROW cobre sete linhas, não sete dias. Para uma janela temporal, use uma expressão de ordenação e um RANGE compatíveis com a versão e o tipo de dado, ou agregue por data antes de usar ROWS.

Cuidados de escala

Uma janela ordenada sem PARTITION BY forma uma única partição lógica e pode concentrar ordenação e estado em um executor. Ela ainda pode ser necessária para ranking global, mas deve ser usada conscientemente e medida na Spark UI. Não invente uma chave de partição apenas para acelerar: isso altera o resultado.

  • Use colunas de desempate para resultados determinísticos.
  • Evite partições extremamente grandes ou muito desbalanceadas.
  • Projete apenas as colunas necessárias antes da janela.
  • Verifique sort, shuffle, spill e duração das tarefas no plano e na UI.

Checklist

  • [ ] A partição representa o grupo lógico correto?
  • [ ] A ordenação é determinística?
  • [ ] O frame expressa linhas ou intervalo de valores como pretendido?
  • [ ] O volume por partição foi medido?

O que é

Extração direta de texto JSON

Explode: uma linha por elemento

explode muda o grão (de pedido para item). Faça isso só quando o grão desejado for o elemento, e leve junto a chave da origem.

SQL
-- Pedido 10 com itens [{cod:1, valor:20}, {cod:2, valor:30}] vira duas linhas
SELECT
    p.id_pedido,
    item.cod   AS cod_item,
    item.valor AS valor_item
FROM silver.pedidos AS p
LATERAL VIEW explode(p.itens) t AS item;

-- Sintaxe equivalente como função de tabela; posexplode traz a posição
SELECT p.id_pedido, e.pos, e.item.cod
FROM silver.pedidos AS p,
     LATERAL posexplode(p.itens) AS e(pos, item);
  • explode descarta linhas com array vazio ou nulo; explode_outer as mantém com NULL.
  • Para transformar arrays sem explodir, use funções de ordem superior: transform, filter, aggregate, exists.
SQL
SELECT id_pedido,
       aggregate(itens, CAST(0 AS DECIMAL(12,2)),
                 (acc, x) -> CAST(acc + x.valor AS DECIMAL(12,2)))           AS total_itens,  -- o acumulador mantém o tipo inicial
       filter(itens, x -> x.valor > 25)                                     AS itens_caros
FROM silver.pedidos;

O tipo VARIANT (Databricks Runtime 15.3+) armazena JSON de forma binária e eficiente, sem schema fixo. É a opção recomendada para dados com estrutura instável que hoje ficam como STRING.

FROM bronze.eventos_variant;

SQL 10 Delta Lake: DML e Manutenção

Aprenda o conceito: trilhas Delta e MERGE idempotente · Cargas full, incremental e CDC — modelo mental, exemplo para prever e erros comuns.

O que é

Delta Lake adiciona log transacional e controle de concorrência a arquivos de dados. Operações, sintaxe e recursos de otimização podem variar por versão do Delta Lake e pelo Databricks Runtime.

Merge

A condição do MERGE deve identificar no máximo uma linha de origem para cada linha de destino. Deduplique ou rejeite ambiguidades antes da operação.

SQL
MERGE INTO gold.vendas AS target
USING silver.vendas_incrementais AS source
ON target.venda_id = source.venda_id
WHEN MATCHED AND NOT (
  target.preco <=> source.preco
) THEN UPDATE SET
  target.preco = source.preco,
  target.atualizado_em = current_timestamp()
WHEN NOT MATCHED THEN INSERT (
  venda_id, preco, atualizado_em
) VALUES (
  source.venda_id, source.preco, current_timestamp()
);

Time travel e restore

SQL
SELECT * FROM gold.vendas VERSION AS OF 42;
RESTORE TABLE gold.vendas TO VERSION AS OF 42;

Time travel depende da disponibilidade do log e dos arquivos referenciados. Um VACUUM pode tornar versões antigas ilegíveis.

Vacuum

SQL
VACUUM gold.vendas RETAIN 168 HOURS;

VACUUM remove arquivos não referenciados mais antigos que a retenção. Antes de reduzir a retenção padrão, avalie leitores concorrentes, operações longas, políticas de recuperação e requisitos de auditoria. Não trate VACUUM como limpeza inofensiva.

Optimize e layout de dados

SQL
OPTIMIZE gold.vendas;

OPTIMIZE compacta arquivos pequenos. Para organizar dados pelas colunas mais filtradas, o Databricks recomenda liquid clustering em tabelas novas, no lugar de PARTITIONED BY e ZORDER.

SQL
CREATE TABLE gold.vendas (venda_id BIGINT, loja_id INT, dt_venda DATE, preco DECIMAL(12,2))
CLUSTER BY (dt_venda, loja_id);

ALTER TABLE gold.vendas CLUSTER BY (loja_id);   -- troca as chaves sem reescrever o histórico
OPTIMIZE gold.vendas;                           -- aplica o clustering incrementalmente
  • Liquid clustering não é compatível com ZORDER nem com particionamento na mesma tabela.
  • Escolha de 1 a 4 colunas a partir dos filtros e joins reais; meça arquivos lidos antes e depois.
  • Com predictive optimization habilitado, OPTIMIZE e VACUUM podem ser executados automaticamente em tabelas gerenciadas pelo Unity Catalog.
  • Referência: Liquid clustering (Databricks).

Checklist

  • [ ] A origem do merge é única pela condição usada?
  • [ ] O merge é idempotente para reprocessamentos?
  • [ ] Retenção e time travel atendem recuperação e auditoria?
  • [ ] A otimização física foi medida no padrão real de consultas?
  • [ ] A funcionalidade existe na versão do ambiente?

SQL 12 Performance Tuning e Leitura de Planos

Aprenda o conceito: trilhas Como o Spark executa seu código · Diagnóstico de performance — modelo mental, exemplo para prever e erros comuns.

Princípio

Otimização começa por evidência: plano físico, métricas da execução, volume lido, shuffle, skew e spill. Evite otimizar apenas pela aparência da consulta.

Reduzir leitura e transferência

O Catalyst pode aplicar column pruning e predicate pushdown quando a fonte e a expressão permitem. Escrever projeções e filtros claros melhora a intenção, mas confirme no plano se foram efetivamente empurrados para a leitura.

SQL
SELECT id_venda, loja_id, valor
FROM vendas
WHERE data_venda >= DATE '2026-01-01';

EXPLAIN FORMATTED
SELECT id_venda, loja_id, valor
FROM vendas
WHERE data_venda >= DATE '2026-01-01';

Procure no plano por filtros na varredura, colunas lidas, exchanges, sorts e estratégia de join. Uma CTE é uma construção lógica; não presuma materialização ou reavaliação sem observar o plano.

Shuffle, skew e spill

  • Shuffle: redistribui dados entre executores; é esperado em joins e agregações, mas volume excessivo merece investigação.
  • Skew: poucas chaves concentram grande parte dos registros, produzindo tarefas muito mais lentas que as demais.
  • Spill: dados intermediários excedem a memória disponível para a operação e usam disco. Pode ser aceitável; impacto e causa devem ser medidos.

AQE pode coalescer partições pós-shuffle e tratar alguns skew joins. Hints como BROADCAST e REPARTITION são intervenções: valide o plano antes e depois.

SQL
EXPLAIN FORMATTED
SELECT /*+ BROADCAST(d) */ f.id_venda, d.categoria
FROM fato_vendas AS f
JOIN dim_produto AS d ON f.produto_id = d.produto_id;

Sequência de diagnóstico

  1. Confirme resultado, grão e volume esperado.
  2. Compare bytes e arquivos lidos com o necessário.
  3. Localize exchanges, sorts, joins e agregações mais caros.
  4. Compare duração e volume das tarefas para detectar skew.
  5. Verifique spill, memória e tamanho das partições.
  6. Altere uma variável por vez e meça novamente.

Checklist

  • [ ] Há filtro seletivo e projeção de colunas?
  • [ ] O plano confirma pruning e pushdown quando aplicáveis?
  • [ ] A estratégia de join é adequada ao tamanho real dos lados?
  • [ ] Shuffle, skew e spill foram medidos?
  • [ ] A mudança preserva o resultado e melhora uma métrica observável?

PySpark 01 Fundamentos: Lazy Evaluation, DAGs e Spark SQL (PySpark)

Aprenda o conceito: trilha Como o Spark executa seu código — modelo mental, exemplo para prever e erros comuns.

O que é

O Spark não executa cada linha de código imediatamente. Transformações montam um plano; ações disparam a execução distribuída desse plano. DataFrame API e SQL compartilham o mesmo otimizador (Catalyst), então você pode alternar entre os dois.

Transformações e ações

Transformações (filter, select, withColumn, join) são lazy: só descrevem um novo DataFrame. Ações (count, show, collect, write) executam o plano.

PYTHON
from pyspark.sql import functions as F

df_filtrado = (
    df_origem
    .filter(F.col("nome").isNotNull())
    .withColumn("idade_ajustada", F.col("idade") + 1)
)  # nada foi lido ainda

df_filtrado.count()                                  # ação: executa o plano
df_filtrado.show(10)                                 # ação: executa de novo (sem cache)
df_filtrado.write.mode("overwrite").saveAsTable("silver.pessoas")
  • Cada ação reexecuta o plano desde a origem, a menos que haja cache. Evite count() de depuração em pipelines de produção.
  • collect() traz todos os dados para o driver: use apenas em resultados pequenos.
  • Narrow transformations (filter, select) não exigem shuffle; wide transformations (groupBy, join, orderBy) redistribuem dados entre executores e criam novos estágios.

DataFrame API vs RDD

RDDs oferecem controle de baixo nível, mas não expõem ao Catalyst a estrutura dos dados. Para transformações tabulares, a DataFrame API permite poda de colunas, pushdown de filtros e escolha de estratégia de join.

PYTHON
df_vendas = spark.read.table("bronze.vendas")
df_fechadas = df_vendas.filter(F.col("status") == "FECHADO")
df_fechadas.explain("formatted")   # mostra o plano físico
  • No Spark Connect (usado pela computação serverless e pelo modo compartilhado do Unity Catalog), a API de RDD e sparkContext não estão disponíveis.

Spark SQL e temp views

PYTHON
df_vendas.createOrReplaceTempView("vw_vendas")

df_resumo = spark.sql("""
    SELECT regiao, COUNT(*) AS transacoes, SUM(valor) AS receita
    FROM vw_vendas
    WHERE valor > 0
    GROUP BY regiao
""")

# Parâmetros nomeados em vez de f-string (Spark 3.4+)
df_regiao = spark.sql(
    "SELECT * FROM vw_vendas WHERE regiao = :regiao",
    args={"regiao": "SUL"},
)
  • Temp views valem para a SparkSession atual. Global temp views (global_temp) valem para a aplicação Spark inteira, não para outros clusters, e não são suportadas em serverless.
  • Montar SQL com f-string a partir de entrada externa abre espaço para SQL injection; prefira args.

Imports e convenções

PYTHON

from pyspark.sql import types as T
from pyspark.sql.window import Window
  • Usar o namespace F. evita sombrear funções nativas do Python (sum, max, round, filter).

  • [ ] As ações no código são intencionais (sem count()/show() de depuração)?
  • [ ] collect()/toPandas() só recebem resultados pequenos?
  • [ ] SQL dinâmico usa parâmetros em vez de concatenação?
  • [ ] O código roda em Spark Connect se o destino for serverless?

O que é

Arquivos com schema explícito

Sem schema, o Spark precisa inferir tipos (passada extra sobre os dados e tipos instáveis entre cargas). Declare o schema em ingestões recorrentes.

df_parquet = spark.read.parquet("/Volumes/main/bronze/landing/parquet/")

JDBC paralelizado

Sem particionamento, uma leitura JDBC usa uma única conexão. Com column, lowerBound, upperBound e numPartitions, o Spark divide a consulta em faixas.

PYTHON
df_erp = spark.read.jdbc(
    url="jdbc:sqlserver://servidor.database.windows.net:1433;database=DB",
    table="vendas.faturamento",
    column="id_venda",
    lowerBound=1,
    upperBound=5_000_000,
    numPartitions=10,
    properties={
        "user": dbutils.secrets.get("erp", "usuario"),
        "password": dbutils.secrets.get("erp", "senha"),
    },
)
  • lowerBound e upperBound não filtram dados: só definem o tamanho das faixas. Linhas fora delas vão para a primeira e a última partição.
  • numPartitions é o número de conexões simultâneas na origem; combine com o dono do banco.
  • Escolha uma coluna numérica/data bem distribuída; uma coluna com skew concentra o trabalho.
  • Alternativa no Databricks: Lakehouse Federation consulta a origem como catálogo, sem código JDBC.

    df_origem

    .withColumn("vl_faturamento", F.col("faturamento").cast(T.DecimalType(18, 2)))
    .withColumn("is_alta_compra", F.col("faturamento") > 1500)   # expressão booleana
)

# Contar o que o cast perdeu (valor presente que virou NULL)
df_tipado.filter(F.col("faturamento").isNotNull() & F.col("vl_faturamento").isNull()).count()
  • Com ANSI ligado (padrão no Spark 4.x e no serverless), cast de valor inválido gera erro. F.try_to_number, F.try_to_timestamp ou expr("try_cast(x AS INT)") devolvem NULL.
  • Use DecimalType para dinheiro; DoubleType é aproximado.

O que é

As operações do dia a dia: projetar, criar e renomear colunas, filtrar, deduplicar, ordenar, empilhar e limpar textos e datas. DataFrames são imutáveis: cada operação devolve um novo DataFrame, então o código é escrito como uma cadeia de métodos.

Projeção, novas colunas e renomeação

PYTHON
from pyspark.sql import functions as F

df_clientes = (
    df_base

df_clientes = df_clientes.withColumns({
    "nome": F.trim(F.upper("nome")),

df_sel = df_bruto.selectExpr("id_pk AS id", "CAST(faturamento AS INT) AS faturamento")

Filtros

Em PySpark, & (e), | (ou) e ~ (não) têm precedência maior que comparações: cada condição precisa de parênteses. Agrupe também a mistura de & e | para deixar a regra explícita.

PYTHON
df_filtrado = df_clientes.filter(
    (F.col("nome").isNotNull() & (F.col("celular") != ""))
    | F.col("status").isin("VIP", "GOLD")

df_sem_banidos = df_filtrado.filter(~F.col("status").isin("BANIDO"))

Deduplicação

dropDuplicates(cols) mantém uma linha qualquer por chave. Ordenar antes com orderBy não garante qual linha fica. Quando a regra é "a mais recente", use janela com desempate.

PYTHON
from pyspark.sql.window import Window

# Qualquer linha por chave (quando as duplicatas são idênticas)
df_unico = df.dropDuplicates(["id_pk", "documento"])

# A linha mais recente por chave, de forma determinística
ultima = Window.partitionBy("id_pk").orderBy(F.col("atualizado_em").desc(), F.col("versao").desc())
df_recente = (
    df.withColumn("rn", F.row_number().over(ultima))
      .filter("rn = 1")
      .drop("rn")
)
  • orderBy global faz shuffle e ordenação de tudo; use só quando a ordem do resultado importa.

PySpark 05 Nulos e Condicionais (PySpark)

Aprenda o conceito: trilha NULL e lógica de três valores — modelo mental, exemplo para prever e erros comuns.

O que é

Como no SQL, null é ausência de valor. Comparações com null resultam em null, então filtros e joins descartam essas linhas sem aviso. Regras de preenchimento e classificação precisam ser explícitas.

when / otherwise e coalesce

PYTHON
from pyspark.sql import functions as F

df_classificado = df_vendas.withColumn(
    "tipo_entrega",
    F.when(F.col("prazo_dias") <= 3, "EXPRESSA")
     .when((F.col("prazo_dias") > 3) & (F.col("status") == "PAGA"), "PADRAO_PAGA")
     .otherwise("PADRAO"),
)

df_seguro = df_classificado.withColumn(
    "id_categoria",
    F.coalesce(F.col("id_categoria"), F.lit(-1)),   # chave do membro "desconhecido"
)
  • Sem otherwise, linhas que não atendem nenhuma condição recebem null.
  • F.col("a").eqNullSafe(F.col("b")) compara tratando null como igual (equivale a <=>).

dropna, fillna e replace

PYTHON
# Remove linhas com nulo apenas nas colunas exigidas pela regra
antes = df_logistica.count()
df_tratado = df_logistica.dropna(how="any", subset=["idade", "cpf"])
print("removidas:", antes - df_tratado.count())

# Preenche por coluna (o tipo do valor precisa ser compatível com o da coluna)
df_imputado = df_logistica.fillna({"idade": 0, "email": "desconhecido@exemplo.com"})

# Strings "vazias" não são null: normalize antes de tratar nulos
df_normalizado = df_logistica.replace(["N/A", "NA", ""], None, subset=["email", "telefone"])
  • dropna sem subset remove a linha por qualquer coluna nula e pode descartar dados válidos.
  • fillna ignora colunas cujo tipo não combina com o valor informado.
  • Preencher com 0 muda médias e somas; registre a regra.

Divisão por zero

Com ANSI ligado (padrão no Spark 4.x e no serverless), divisão por zero gera erro. Defina a política explicitamente.

PYTHON
df_rentabilidade = df.withColumns({
    "rentabilidade":      F.try_divide("receita", "custo"),    # Spark 3.5+: null se custo = 0
    "rentabilidade_when": F.when(F.col("custo") == 0, None)
                           .otherwise(F.col("receita") / F.col("custo")),
    "is_custo_zero":      (F.col("custo") == 0).cast("int"),   # flag para medir o caso
})

Checklist

  • [ ] Toda cadeia when tem otherwise?
  • [ ] Strings vazias e marcadores ("N/A") foram normalizados antes de tratar nulos?
  • [ ] Linhas removidas por dropna são contadas?
  • [ ] Divisões têm política para denominador zero?

PySpark 06 Agrupamentos, Agregações e Pivots (PySpark)

O que é

groupBy().agg() resume linhas em métricas por grupo. pivot gira valores de uma coluna em colunas; unpivot faz o inverso. Calcular todas as métricas em um único agg evita várias passadas sobre os dados.

Várias agregações em uma passada

PYTHON
from pyspark.sql import functions as F

df_resumo = (
    df_fatos
    .groupBy("ano_fiscal", "uf")
    .agg(
        F.count("id_transacao").alias("qtd_vendas"),
        F.round(F.avg("lucro"), 2).alias("lucro_medio"),
        F.count_if(F.col("status") == "ERRO").alias("qtd_erros"),          # Spark 3.5+
        F.sum(F.when(F.col("canal") == "LOJA", F.col("valor"))).alias("valor_loja"),
        F.approx_count_distinct("id_cliente", rsd=0.02).alias("clientes_aprox"),
    )
)

# Agregação sem agrupamento: uma linha com o total
total = df_fatos.agg(F.sum("valor").alias("total")).first()["total"]
  • approx_count_distinct usa HyperLogLog++ com erro relativo padrão de 5% (rsd=0.05). Valores menores de rsd aumentam precisão e memória. F.count_distinct é exato, porém mais caro em alta cardinalidade.
  • Use F.sum, F.max, F.round com o namespace: importar sum/round diretamente sombreia as funções do Python.

Pivot

PYTHON
df_pivotado = (
    df_vendas
    .groupBy("categoria")
    .pivot("ano", [2023, 2024, 2025])   # lista explícita
    .agg(F.sum("receita"))
)
# | categoria | 2023 | 2024 | 2025 |
  • Sem a lista de valores, o Spark executa uma consulta extra para descobri-los, e o número de colunas passa a depender dos dados.

Unpivot (melt)

PYTHON
df_longo = df_planilha.unpivot(          # Spark 3.4+ (alias: melt)
    ids=["regiao"],
    values=["receita_jan", "receita_fev", "receita_mar"],
    variableColumnName="mes",
    valueColumnName="receita",
)
  • As colunas em values precisam ter tipos compatíveis.

Subtotais: rollup e cube

PYTHON
df_subtotais = (
    df_vendas
    .rollup("pais", "regiao")
    .agg(F.sum("valor").alias("valor"), F.grouping_id().alias("nivel"))
)
  • rollup gera (pais, regiao), (pais) e o total; cube gera todas as combinações. grouping_id distingue subtotal de null real.

Checklist

  • [ ] Todas as métricas do grupo estão em um único agg?
  • [ ] O erro aceitável de contagens aproximadas foi definido?
  • [ ] O pivot recebe a lista de valores?
  • [ ] O grão do resultado está documentado?

PySpark 07 Joins em PySpark

Aprenda o conceito: trilha Grão e cardinalidade — modelo mental, exemplo para prever e erros comuns.

O que são

DataFrame.join combina DataFrames por nomes de colunas ou expressões. Em escala, avalie cardinalidade, volume de shuffle, distribuição das chaves e estratégia física.

Chaves com o mesmo nome

Passar os nomes em on mantém uma única cópia dessas colunas no resultado. Isso resolve a ambiguidade de nomes, mas não remove linhas duplicadas nem altera a cardinalidade.

PYTHON
df_resultado = df_vendas.join(
    df_lojas,
    on=["loja_id"],
    how="left",
)

Para nomes diferentes ou condições compostas, use aliases e projete explicitamente a saída.

PYTHON
from pyspark.sql import functions as F

v = df_vendas.alias("v")
c = df_cambio.alias("c")

df_convertido = (
    v.join(
        c,
        (F.col("v.moeda") == F.col("c.codigo"))
        & (F.col("v.data_venda") == F.col("c.data_referencia")),
        "left",
    )
    .select("v.*", F.col("c.taxa").alias("taxa_cambio"))
)

Semi e anti join

PYTHON
df_com_acesso = df_clientes.join(df_acessos, "cliente_id", "left_semi")
df_sem_acesso = df_clientes.join(df_acessos, "cliente_id", "left_anti")

Essas estratégias filtram a esquerda sem transportar colunas da direita.

Broadcast

broadcast() é apropriado quando o DataFrame transmitido cabe com folga na memória de cada executor. Estatísticas desatualizadas ou dados maiores que o esperado podem tornar a decisão pior que um shuffle join.

PYTHON
from pyspark.sql.functions import broadcast

df_resultado = df_fato.join(
    broadcast(df_dimensao_pequena),
    on="produto_id",
    how="left",
)

df_resultado.explain("formatted")

Cuidados

  • Valide duplicidades por chave antes de assumir relação 1:1.
  • Alinhe os tipos das chaves antes do join.
  • Não use dropDuplicates para esconder cardinalidade inesperada.
  • Compare contagens e métricas segundo o grão esperado.
  • Para skew, meça a distribuição e avalie AQE antes de aplicar salting.

Checklist

  • [ ] O grão de cada DataFrame é conhecido?
  • [ ] O tipo de join preserva as linhas pretendidas?
  • [ ] A projeção evita colunas duplicadas ou desnecessárias?
  • [ ] O plano confirma broadcast, sort-merge ou outra estratégia esperada?

PySpark 08 Window Functions em PySpark

Aprenda o conceito: trilha Window functions — modelo mental, exemplo para prever e erros comuns.

O que são

Uma WindowSpec define o grupo lógico, a ordenação e o frame usados por funções como row_number, lag e agregações acumuladas.

Deduplicação determinística

PYTHON
from pyspark.sql import functions as F
from pyspark.sql.window import Window

por_dispositivo = Window.partitionBy("dispositivo_id").orderBy(
    F.col("extraido_em").desc(),
    F.col("evento_id").desc(),
)

df_atual = (
    df_eventos
    .withColumn("ordem", F.row_number().over(por_dispositivo))
    .filter(F.col("ordem") == 1)
    .drop("ordem")
)

O desempate evita escolher linhas arbitrárias quando timestamps são iguais.

Lag e acumulado

PYTHON
ordem_cliente = Window.partitionBy("cliente_id").orderBy("evento_em", "evento_id")

df_variacao = df_eventos.withColumn(
    "valor_anterior",
    F.lag("valor").over(ordem_cliente),
)

acumulado_conta = (
    Window.partitionBy("conta_id")
    .orderBy("data_movimento", "movimento_id")
    .rowsBetween(Window.unboundedPreceding, Window.currentRow)
)

df_saldo = df_movimentos.withColumn("saldo", F.sum("valor").over(acumulado_conta))

Frames e tempo

PYTHON
ultimas_sete_linhas = (
    Window.partitionBy("segmento")
    .orderBy("data_referencia")
    .rowsBetween(-6, Window.currentRow)
)

Esse frame cobre sete linhas, não sete dias. Se houver datas ausentes ou múltiplas linhas por dia, agregue previamente no grão diário ou use um rangeBetween coerente com a expressão numérica de ordenação.

Cuidados de escala

Uma janela ordenada sem partitionBy cria uma partição lógica global. Isso pode ser correto para ranking global, mas concentra a ordenação; confirme o custo no plano e na Spark UI. Acrescentar uma partição artificial muda a semântica e não é uma correção neutra.

  • Observe skew e volume dentro de cada grupo.
  • Reduza colunas antes da janela quando possível.
  • Use ordem determinística.
  • Meça sort, shuffle e spill.

Checklist

  • [ ] Partição e ordenação representam a regra de negócio?
  • [ ] Empates têm critério explícito?
  • [ ] O frame significa linhas ou intervalo de valores como pretendido?
  • [ ] O tamanho das partições foi observado?

PySpark 09 JSON, Structs e Schemas (PySpark)

O que é

Dados semiestruturados exigem distinguir texto JSON (StringType) de colunas já tipadas (StructType, ArrayType, MapType). Um schema explícito torna o contrato observável; registros incompatíveis ainda precisam ser medidos e tratados.

Acessar campos de structs e de texto JSON

PYTHON
from pyspark.sql import functions as F

# Coluna struct já tipada: notação de ponto
df_proto = df_ingestao.select(
    "id_registro",
    F.col("metadata.rede.versao_tls").alias("versao_tls"),

df_ids = df_bronze.withColumn(
    "id_core",
    F.get_json_object("payload_txt", "$.root.identificadores[0].idCore"),
)
  • get_json_object reprocessa o texto a cada chamada. Para vários campos, converta uma vez com from_json.

Explode de arrays

explode gera uma linha por elemento e muda o grão do DataFrame.

PYTHON
df_tags = (
    df_receitas
    .withColumn("tags", F.split("tags_texto", ","))
    .withColumn("tag", F.explode_outer("tags"))   # mantém linhas com array vazio/nulo

# Transformar sem explodir: funções de ordem superior
df_itens = df_pedidos.withColumns({
    "itens_caros": F.filter("itens", lambda x: x["valor"] > 25),
    "total":       F.aggregate(
        "itens",
        F.lit(0).cast("decimal(12,2)"),
        lambda acc, x: (acc + x["valor"]).cast("decimal(12,2)"),   # acumulador mantém o tipo inicial
    ),
})
  • explode descarta linhas com array vazio ou nulo; explode_outer as preserva com null.
  • posexplode também devolve a posição do elemento.

Schema explícito na leitura e from_json

PYTHON
from pyspark.sql import types as T

schema_vendas = T.StructType([
    T.StructField("id_venda", T.StringType(), nullable=False),
    T.StructField("valor", T.DecimalType(12, 2), nullable=True),
    T.StructField("_corrupt", T.StringType(), nullable=True),
])

df_vendas = (
    spark.read
    .schema(schema_vendas)
    .option("columnNameOfCorruptRecord", "_corrupt")
    .json("/Volumes/main/bronze/landing/vendas/")

df_vendas.filter(F.col("_corrupt").isNotNull()).count()   # registros que não seguiram o schema

# Texto JSON em uma coluna → struct tipada
schema_evento = "STRUCT<nome: STRING, idade: INT, ativo: BOOLEAN>"   # DDL também é aceito
df_evento = df_bronze.withColumn("evento", F.from_json("payload_txt", schema_evento))
  • nullable=False no schema de leitura não rejeita nulos em arquivos: valide depois.
  • F.schema_of_json ajuda a sugerir um schema a partir de um exemplo; fixe o resultado no código em vez de inferir em produção.

Colunas obrigatórias ausentes

Quando cargas diárias podem omitir campos, adicione os ausentes com tipo explícito para manter o schema estável.

PySpark 10 Delta Lake API em PySpark

Aprenda o conceito: trilhas Delta e MERGE idempotente · Cargas full, incremental e CDC — modelo mental, exemplo para prever e erros comuns.

O que é

DeltaTable expõe operações transacionais em Python. SQL continua sendo uma alternativa válida; escolha a interface que deixa a transformação mais clara e testável.

Merge

PYTHON
from delta.tables import DeltaTable

target = DeltaTable.forName(spark, "gold.vendas")

(
    target.alias("t")
    .merge(
        df_incremental.alias("s"),
        "t.venda_id = s.venda_id",
    )
    .whenMatchedUpdate(
        condition="NOT (t.preco <=> s.preco)",
        set={
            "preco": "s.preco",
            "atualizado_em": "current_timestamp()",
        },
    )
    .whenNotMatchedInsert(
        values={
            "venda_id": "s.venda_id",
            "preco": "s.preco",
            "atualizado_em": "current_timestamp()",
        },
    )
    .execute()
)

Garanta que a origem tenha no máximo uma linha por chave de merge e defina uma política de desempate antes da escrita.

Evolução de schema

PYTHON
(
    df_com_novas_colunas.write
    .format("delta")
    .mode("append")
    .option("mergeSchema", "true")
    .saveAsTable("silver.clientes")
)

mergeSchema pode adicionar colunas compatíveis, mas não substitui contrato de dados. Valide nomes inesperados, tipos, nulabilidade e impacto nos consumidores. O comportamento exato depende da versão e da operação.

PySpark 11 Databricks Utilities (dbutils)

O que é

dbutils é a biblioteca de utilitários dos notebooks e jobs Databricks: manipula arquivos, recebe parâmetros (widgets) e lê segredos. Existe apenas no Databricks; código que depende dele não roda em Spark local sem adaptação.

Arquivos: dbutils.fs e Volumes

Com Unity Catalog, arquivos não tabulares ficam em Volumes (/Volumes/<catálogo>/<schema>/<volume>/), com permissões governadas pelo catálogo. Mounts (/mnt) e a raiz do DBFS são legado.

PYTHON

for f in arquivos:
    print(f.name, f.size, f.modificationTime)

dbutils.fs.cp("/Volumes/main/silver/arquivos/relatorio.csv",
              "/Volumes/main/silver/arquivos/bkp/relatorio.csv")

dbutils.fs.rm("/Volumes/main/bronze/arquivos/tmp_carga/", recurse=True)   # irreversível
  • Volumes também aceitam APIs locais de arquivo (open, os, shutil) no caminho /Volumes/....
  • rm com recurse=True apaga sem lixeira: confira o caminho (de preferência parametrizado e validado) antes.
  • Nunca apague com dbutils.fs.rm arquivos dentro do diretório de uma tabela Delta; use DELETE/VACUUM.

Parâmetros: widgets e job parameters

Widgets recebem valores do usuário no notebook ou de parâmetros do job, evitando datas e ambientes fixos no código.

Percentual de nulos por coluna

PYTHON
def percentual_nulos(df, colunas):
    linha = df.select([
        (F.avg(F.col(c).isNull().cast("int")) * 100).alias(c) for c in colunas
    ]).first()
    return linha.asDict()

nulos = percentual_nulos(df_clientes, ["telefone", "email", "cpf"])
violacoes = {c: p for c, p in nulos.items() if p > 25.0}
if violacoes:
    print(f"Alerta de qualidade: nulos acima de 25% em {violacoes}")
  • O limite (25% acima) é exemplo: defina-o com o consumidor do dado.

Perda de linhas em joins

Compare a origem com o resultado e isole as linhas sem correspondência, em vez de só contar.

PYTHON
sem_dimensao = df_vendas.join(df_produtos, "id_produto", "left_anti")
qtd_orfas = sem_dimensao.count()
total = df_vendas.count()

if total and qtd_orfas / total > 0.01:

AQE e partições

AQE pode ajustar o plano com estatísticas de runtime, coalescer partições pós-shuffle e tratar alguns skew joins. Em runtimes gerenciados, confira os defaults antes de sobrescrever configurações.

PySpark 14 Medalhao: Bronze, Silver e Gold no Databricks

O que e

A arquitetura medalhao organiza os dados em camadas com papeis diferentes ao longo do pipeline. Ela ajuda a separar ingestao, confiabilidade estrutural e consumo analitico, reduzindo acoplamento e melhorando rastreabilidade.

No contexto Databricks, essa separacao tambem ajuda a decidir: - onde aplicar limpeza - onde tipar - onde deduplicar - onde enriquecer - onde agregar - onde expor para BI ou consumo final

1. Papel de cada camada

Bronze

Camada mais proxima da origem.

Objetivo - preservar o dado ingerido - manter rastreabilidade - registrar contexto de carga

O que normalmente entra aqui - dados crus ou quase crus - schema proximo da origem - arquivos, tabelas ou streams ingeridos - metadados tecnicos de ingestao

O que evitar - regras de negocio pesadas - limpeza destrutiva - agregacoes - joins de consumo

Silver

Camada de confiabilidade estrutural.

Objetivo - transformar o dado cru em dado utilizavel - corrigir tipos - tratar nulos e padroes - deduplicar quando necessario - padronizar chaves e nomes

O que normalmente entra aqui - entidades limpas - eventos confiaveis - tabelas com schema estabilizado - regras de qualidade e enriquecimento leve

O que evitar - tabelas excessivamente agregadas - metricas de dashboard especificas - logicas altamente dependentes de um unico consumidor

Gold

Camada de consumo.

Objetivo - entregar dados prontos para analise - organizar marts, fatos, dimensoes e tabelas analiticas - otimizar acesso de BI, analytics e consumo de negocio

O que normalmente entra aqui - tabelas fato - dimensoes - tabelas agregadas - visoes de negocio - datasets finais para dashboard

O que evitar - virar deposito de toda regra da empresa sem criterio - duplicar muitas versoes do mesmo dataset sem necessidade - carregar complexidade tecnica que deveria ter sido resolvida na Silver

2. Como pensar granularidade

Granularidade deve ficar clara em cada camada.

Bronze

  • normalmente segue o grao da origem
  • 1 linha pode significar 1 evento cru, 1 registro operacional ou 1 documento ingerido

Silver

  • deve representar um grao confiavel e estavel
  • 1 linha precisa ter significado claro para engenharia e consumo intermediario
  • deduplicacao e padronizacao costumam acontecer aqui

Gold

  • o grao deve refletir o caso de uso analitico
  • pode ser transacional, snapshot, acumulativo ou agregado
  • precisa estar explicito para evitar KPI errado

3. O que costuma ser feito em cada camada

Bronze

  • ingestao de arquivos/tabelas
  • captura de metadados de carga
  • particionamento tecnico de aterrissagem quando fizer sentido
  • armazenamento do dado bruto

Silver

  • cast e tipagem
  • tratamento de nulos
  • limpeza de strings
  • padronizacao de nomes
  • deduplicacao
  • validacao de chaves
  • enriquecimento leve
  • conformacao entre fontes

Gold

  • joins orientados a consumo
  • modelagem dimensional
  • regras de negocio consolidadas
  • agregacoes e marts
  • semanticas de indicadores
  • tabelas finais para BI, analytics e reporting

4. Colunas tecnicas uteis

Nem toda coluna tecnica precisa existir em toda camada, mas estas sao comuns:

  • ingestion_ts
  • load_date
  • source_system
  • source_file
  • record_hash
  • is_current
  • effective_start_date
  • effective_end_date
  • update_ts

Heuristica

  • Bronze: priorize rastreabilidade
  • Silver: priorize confiabilidade e controle
  • Gold: mantenha apenas o que ajuda consumo, auditoria ou historizacao

5. Regras praticas de qualidade por camada

Bronze

  • o dado chegou?
  • chegou completo?
  • a origem foi identificada?

Silver

  • tipos estao corretos?
  • nulos criticos foram tratados?
  • o grao esta consistente?
  • ha duplicidades indevidas?

Gold

  • a semantica do indicador esta correta?
  • o join preserva a cardinalidade esperada?
  • o dataset final esta pronto para consumo sem ambiguidade?

6. Erros comuns

  • fazer limpeza destrutiva na Bronze
  • pular a Silver e transformar a Bronze direto em dataset final
  • colocar regra de dashboard na Silver
  • agregar cedo demais e perder flexibilidade analitica
  • deixar Gold com cara de camada tecnica, e nao de consumo
  • nao explicitar o grao final da tabela

7. Heuristica de decisao rapida

  • Se a tabela existe para preservar a origem: Bronze
  • Se a tabela existe para tornar o dado confiavel e reutilizavel: Silver
  • Se a tabela existe para analise, KPI ou BI: Gold
